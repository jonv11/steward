# 13 — Change dates are UTC, and untracked pages escape them in the working tree

Type: bug
Category: bug
Blocked by: None — can start immediately

## Problem

the `local-change-date` source of `frontmatter-auto` writes the UTC date, and a working-tree check does not count an untracked page as changed. When the local date differs from the UTC date, a new page dated today passes `steward check` in the working tree but fails STWD-007 once it is staged and checked from a snapshot, for example in a pre-commit gate.

`src/Steward.Core/Maintenance/FrontmatterAutoMaintainer.cs:118` returns `DateTime.UtcNow`, and only for files in `context.ChangedFiles`.

## Reproduce

 (found in the mpes repo, its inbox/24; pinned revision b90bcaa):

1. Set `TZ='XYZ-16'` (local 2026-11-17, UTC 2026-11-16).
2. Add a new page with `updated: 2026-11-17` and run `steward maintain --apply` twice. The page keeps 2026-11-17 and `steward check` passes.
3. Stage it and check a no-checkout snapshot of the index. STWD-007: "Update frontmatter field 'updated'" on the new page, which now expects 2026-11-16.
4. The control with `TZ=UTC` and the page dated 2026-11-16 passes both checks.

In CET this bites between 00:00 and 01:00.

## Suggested direction

one date for "today", the same in the working tree and the snapshot. Either use the local date as the name says, or make the UTC choice configurable or documented. Treat untracked files as changed, so the working tree applies the same date the snapshot will expect.

## Acceptance criteria

- [ ] `local-change-date` writes the local date, as its name says
- [ ] A working-tree check treats untracked files as changed, so it expects the date a snapshot of the staged file will expect
- [ ] Tests pin both, independent of the machine's time zone
