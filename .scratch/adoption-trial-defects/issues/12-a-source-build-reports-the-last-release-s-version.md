# 12 — A source build reports the last release's version

Status: done
Type: bug
Category: bug
Blocked by: None — can start immediately

> *This was generated by AI.*

## Problem

a build from any commit reports the last release's version. mpes ran Steward built from `b90bcaa`, 64 commits past `v0.18.1`, and `steward version` printed `steward 0.18.1` there and from the installed `v0.18.1` tool. The two behave differently: the release cannot parse mpes's `.steward/policy.yaml` (`index_pattern`). `Directory.Build.props` sets `InformationalVersion` to `$(Version)`, so the `SourceRevisionId` that mpes passed to `dotnet publish` was dropped.

## Suggested direction

`steward version` (text and JSON) shows the commit for non-release builds, e.g. `0.19.0-dev+b90bcaa` or at least `0.18.1+b90bcaa`. A tagged release build keeps the plain version. Then an agent comparing behaviour can tell which build it has.

## Acceptance criteria

- [x] `steward version` text names the commit for a build that is not a release, e.g. `steward 0.19.0+b90bcaa (source build)`
- [x] JSON keeps `version` as `x.y.z` and adds `commit` and `releaseBuild`
- [x] The release script marks its builds, which print the plain version

## Answer

Done in 740a92b. An AssemblyMetadata StewardReleaseBuild item carries -p:StewardReleaseBuild=true, which Build-ReleaseAssets.ps1 now passes to pack and publish. Any other build prints 'steward X+SHA (the short commit) (source build, not a release)', taking the commit the SDK appends to the informational version. JSON keeps version as x.y.z, so existing parsers such as mpes's still work, and adds commit and releaseBuild (schema updated). Checked a release-flagged build prints 'steward 0.19.0'; VersionCommandTests covers both forms.
